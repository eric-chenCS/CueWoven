# Recall v2.14 — safer capture holds and accurate subtitle deduplication

Version **2.14.0** adapts the useful ideas in the supplied v2.13 patch and fixes the accuracy/concurrency problems found during review. It keeps one combined search and the existing scene/audio models.

## Changes

- **Delete, Clear and restore requests hold live visual capture.** Exclusive access is reserved before awaiting anything. Pending OCR is canceled, in-flight scene saves are invalidated, and the action waits for captures, scene queries and visual-model warmup to drain. New visual captures report busy until it finishes. A simultaneous restore/delete/clear request receives a clear error rather than overlapping writes. Each backup batch owns its hold; the settings page disables its destructive controls during the full restore. Another library page can act between completed batches. Speech-to-text must still be stopped and caption fetching paused before destructive actions/restoring. Capture can resume afterward and save newly watched frames.
- **Exact subtitle-line deduplication.** OCR now retains individual line boundaries. Newly recognized lines are compared with up to 30 recent rows within 30 video seconds. Matching is conservative: normalized case/spacing must match the whole ordered line. Changing a number, adding “not,” or reversing names keeps the new text. A persistent watermark alongside a changing subtitle is omitted from the new searchable passage; bounded observation metadata supports that comparison and survives backup restore. Distant occurrences may be saved again with their own timestamp. OCR errors may still create near-duplicate lines; accuracy takes priority over aggressive fuzzy deletion.
- **Sharp-pixel frame checks.** The low-resolution 64 × 36 threshold from the supplied patch is not shipped. Every eligible five-second attempt hashes the actual sharp RGBA pixels, up to 1280 × 720, before JPEG encoding. Identical pixels can skip one recognition cycle, but eligible unchanged frames are re-read after 10 wall seconds or a playback revision/large seek. New pixels continue on the five-second cadence, including after empty OCR results. The proposed 10-second empty-frame backoff is not shipped. As before, previously sampled five-second video buckets, paused/hidden/advertising/seeking players and background history-capture tabs are excluded.
- **Three-second playback lead-in.** Only the result's playback target moves earlier, clamped to zero. The observed timestamp remains unchanged in storage, result metadata, deduplication and scene fusion. The result timestamp tooltip explains both times. Transcript/audio timestamps keep their existing behavior.
- **Fewer repeated embeddings/index rebuilds.** Frames whose recognized lines are all recent exact repeats return without embedding or saving a new OCR row. The index rebuild implementation is unchanged. The obsolete scene-busy retry in the backup helper is removed; arbitrary errors are not replayed after possible partial writes. Scene-only backup batches now invalidate the cached scene counts.

The 240-scenes-per-video / 2,000-total / 24 MiB scene payload limits stay the same. OCR still caps text at 720 rows per video and 10,000 total. No dependency, model, browser permission or IndexedDB schema version changes. The new bounded observation metadata is optional, so existing rows and older backups still load. Full caption replacements preserve OCR data.

## Validation

All **156 Node tests** pass. Added regressions cover reservation before waiting, conflicting mutations, draining captures/queries/warmup, failure cleanup, individual OCR lines, changed digits/negation/order, bounded metadata, time-window behavior, original timestamps versus playback lead-in, exact pixels, periodic reads during slow playback, and continued five-second sampling after empty/busy responses. Initially, removing the wall-time reread guard survived the normal-speed test because video time also triggered rereading; a slow-playback regression was added and then caught that mutation. The original guard was restored and the suite passed.

Real-model isolated Chromium tests passed:

- **Automatic changing subtitles:** a canvas-backed video changed “The dose is 10 mg.” to “The dose is 11 mg.”, then “The battery is safe to use.” to “The battery is not safe to use.” All four passages were saved separately. NEWS LIVE appeared once in searchable text; later changing passages excluded the watermark. Eleven seconds of unchanged playback created no extra rows. A quoted negative query returned the “not safe” passage.
- **Library contention:** restoring a scene while CLIP text search ran succeeded. A concurrent Clear request was refused while restore held access. Delete and Clear during actual OCR both succeeded, canceled the pending save, left no deleted video/OCR rows behind, and allowed a later new capture to save normally.
- **Existing regressions:** OCR/search/timestamp-link/file-input backup, import provenance/title notices and restore during scene capture, default keyboard behavior, real CLIP scene/retention/backup limits, legacy embedding migration, single-video arrows, refinement, actual Whisper player-audio capture and the six-player background caption queue passed. The browser-test URL assertion now checks the playback lead-in while retaining the original observed timestamp. Light/dark result screenshots were inspected.

A static-canvas microbenchmark at 1280 × 720 measured median old JPEG-encode/hash work at 3.5 ms, the new unchanged-pixel check at 3.1 ms, and changed-pixel check plus JPEG encoding at 6.5 ms. It used 20 iterations on one machine and excludes video decode, OCR/model inference and sustained resource use. The temporary raw pixel buffer is at most 3,686,400 bytes; only the fingerprint survives between checks. Periodic rereading of static frames can use more OCR work than v2.13's indefinite exact-image skip. Moving frames still incur OCR every eligible five seconds. These measurements do not guarantee lag-free playback on every device.

The runtime/dependency graph is unchanged. Native pnpm audit still reports the existing 3 high sharp and 1 moderate sprintf-js advisories in native Node paths excluded from the browser bundle; the source graph remains not audit-clean. No new public YouTube playback test was run for v2.14. Video pixels, audio fixtures and caption outcomes in regression tests are controlled; media playback, OCR, MiniLM, CLIP, Whisper, IndexedDB and extension code are real.

## Update

Keep the installed folder path unchanged, reload Recall at edge://extensions or chrome://extensions, refresh YouTube tabs and reopen the popup/settings. It should show **2.14.0**. Updating from v2.13 needs no runtime rebuild; teammates pull and reload. Older checkouts need `pnpm run setup` for the existing bundled OCR runtime. The packaged ZIP contains it. Existing history, captions, scenes and OCR text need no re-import. The previous installed folder is backed up before copying the tested package.

Recognition is English-only and sampled, so brief, stylized, small or protected subtitles may be missed. Playback links provide a three-second lead-in, not an exact subtitle onset/end range. This update does not add simultaneous multi-video speech recognition or guarantee coverage of every visible window.
